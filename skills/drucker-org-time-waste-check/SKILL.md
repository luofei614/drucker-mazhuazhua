# 组织时间浪费四类体检（含会议病的诊断与处方）

## R — 原文 (Reading)

> 危机如果已是第二次发生，那无论如何不能让它发生第三次。……管理良好的组织是"无趣"的组织。富有"戏剧性"的工厂，也就是让"工业的史诗"展现在参观者眼前的工厂，是管理不善的工厂。……会议在本质上是对组织结构有缺陷所做的补救。……如果管理者用来开会的时间超过一定比例（全部时间的一小部分），就足以证明这个组织的结构有缺陷。
>
> — 德鲁克，第2章 认识你的时间

## I — 方法论骨架 (Interpretation)

德鲁克认为，管理者的时间浪费有两类来源：一类是自己可控的（用 `drucker-time-log-consolidate` 处理），另一类是**组织和管理不善造成的**——这一类个人再努力也解决不了，但必须先被识别出来。

这个 skill 的价值在于它给出了**可量化的阈值**，把"感觉很忙"变成"可以测量"：

| 病症 | 量化判据 | 病因 |
|---|---|---|
| 反复发生的危机 | 同一危机出现**第二次** | 缺少体系或远见，没有把意外转化为常规工作 |
| 人员过剩 | 高层处理人际摩擦的时间 **> 1/10** | 人越多，时间越用于相互交流而不是工作 |
| 组织结构缺陷 | 会议时间 **≥ 1/4** | 本该由一个职位/部门完成的工作被分散了 |
| 信息功能失灵 | 信息未送达需要的人，或格式不对 | 发送者按自己的需要而非使用者的需要设计信息 |

最反直觉的一条是：**会议不是协作的体现，而是组织设计缺陷的补救措施**。如果结构完美，就不需要开会。所以治会议病不能靠"少开点会"，而要靠修结构；对那些**必须开的会**，才用会议三件套（见 E 段第 5 步）保证它不浪费时间。

配套的价值观判据：**管理良好的组织是"无趣"的组织**。救火英雄、戏剧性的战斗、热火朝天的工厂，都是管理不善的症状。

## A1 — 书中的应用 (Past Application)

### 案例 1：某财务副总的会议
- **问题**：这位副总长期觉得会议太多，却没有数据。
- **方法论的使用**：他做了时间记录，发现开会占用了很大比例；然后不是"少开点会"，而是追问"为什么需要这些会"——发现是本该由一个部门完成的职责被分散在几个部门之间。
- **结论**：会议数量是结构缺陷的症状指标，不是可以单独优化的独立变量。
- **结果**：调整职责划分后，从"十几个人开一下午"压到"三个人开一小时"。

### 案例 2：给生产部门送平均数
- **问题**：总部给生产部门的是**平均数**报表，而生产真正需要的是范围与极值（最高/最低、波动区间）。
- **方法论的使用**：德鲁克用它演示"信息格式失灵"——信息送达了，但对使用者无用，等于没送。
- **结论**：信息的正确性不由发送方定义，而由使用者的需要定义（与"贡献由接收方定义"同源）。
- **结果**：这不是一个加工作量的事，是一个问一句"你需要什么格式"就能修的事。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. "会议太多了""一天都在会上"——需要判断这是协作需求还是结构缺陷。
2. 同类危机反复出现（第二次以上），每次都靠临时救火解决。
3. 组织刚加完人，但交付反而变慢；或高层大量时间花在调解人际摩擦上。
4. 一线抱怨总部给的报表/数据"没用""要花几小时换算"。
5. 全员远程/异步协作、会议很少，但交付依然慢——此时浪费已从"会议"迁移到"信息格式失灵"这一支。

### 语言信号（用户的话里出现这些就应激活）

- "会议太多了" / too many meetings / 一天都在开会
- "怎么又出这个问题" / 反复出问题 / 危机不断 / firefighting
- "人越多越慢" / 人浮于事 / 加了人还是慢
- "这个报表根本没法用" / 数据不对 / 一线抱怨
- "组织效能怎么提升" / why is everything so slow

### 与相邻 skill 的区分

- 与 `drucker-time-log-consolidate` 的区别：那个是**个人层**（记录你自己的时间、砍你自己能控制的浪费、产出整块时间）；本 skill 是**组织层**。判据很简单：如果这件事你一个人就能改，用个人层；如果需要动职责、动编制、动信息流，用本 skill。
- 与 `drucker-job-redesign` 的区别：职位重设计处理的是**单个职位**设计错误（连续挫败 2–3 个优秀者）；本 skill 看的是**整体结构**（责任分散、信息未送达）。前者是点，后者是面。
- 与 `drucker-contribution-triangle` 的区别："信息格式不对"表面像沟通问题，实质是贡献问题——信息的贡献由接收方定义。若根因是"没人问过接收方要什么"，两个 skill 会同时适用，但本 skill 给的是结构性修法。

## E — 可执行步骤 (Execution)

1. **测四个数**（这是本 skill 的入口，不能跳过）
   - 问：同一类危机今年出现过几次？≥2 次 → 记为病症 ①
   - 问：你（或高层）处理人际摩擦、调解争议的时间占比？> 1/10 → 记为病症 ②
   - 问：你开会的时间占比？≥ 1/4 → 记为病症 ③
   - 问：有没有人收到过"送错了"或"格式不对"的信息？（如给生产的是平均值，而它要范围与极值）→ 记为病症 ④
   - 完成标准：四个数都有明确答案（不接受"大概""应该没有"）。
   - 判停条件：若四个数都测不出来 → **先回到 `drucker-time-log-consolidate` 做个人实录**，没有数据就没有诊断。

2. **病症 ① 反复危机 → 转化为常规工作**
   - 做法：把第二次出现的危机，变成未经训练的人也能照做的例行程序。
   - 完成标准：写出一份"下次发生时的处理步骤"，且能交给一个不了解背景的人执行。
   - 判停条件：若该危机涉及外部环境剧变而无法程序化，转为建立预警指标而非流程。

3. **病症 ② 人员过剩 → 重新审视常备能力**
   - 做法：只在"主要工作中每天都用得上"的技能才常备在团队内，其余外取。
   - 完成标准：列出团队常备技能清单，标出哪些是每天用、哪些不是。
   - 判停条件：**若减员不在你的权限内，明确告知用户这是组织决策，个人层面只能做到"不再新增"**——不要假装个人能解决。

4. **病症 ③ 会议泛滥 → 修结构，而不是砍会议**
   - 做法：追问"为什么这项工作需要通过会议协调"——通常是本该由一个职位/部门完成的工作被分散了。
   - 完成标准：指出至少一处"分散的责任"，并提出合并方案。
   - 判停条件：若责任分散涉及跨部门边界且超出用户权限，明确标为"需上一级决策"。

5. **病症 ④ 信息失灵 → 问接收方要什么格式**
   - 做法：直接问信息的使用者"你需要什么、什么时候要、以什么形式要"。
   - 完成标准：至少改掉一处"发送方觉得有用、接收方觉得没用"的信息。
   - 典型修法：把平均值换成范围与极值；把会议纪要换成可检索的结构化上下文。

6. **对必须开的会，用会议三件套**（处方部分）
   - 会前：明确会议类型——**是要做决策，还是为了通报情况，或者弄清楚大家应该干什么？** 目的不明就不开会。
   - 会中开场：阐明具体目的与预期成果，并引导会议达成它。通报会不要变成吹牛会，创见会不要变成某人的报告会。**主持者可以主持并听取要点，也可以作为参会人讨论，但不可二者兼得。**
   - 收尾：呼应开场，阐述最终结论与最初意图之间的关系。
   - 完成标准：结束时能说出这次会属于哪一类目的、达成了什么成果。
   - 判停条件：开到一半发现目的不明 → 停下来先定目的，或散会。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **个人时间不够用**：那是 `drucker-time-log-consolidate` 的场景，不要拿组织诊断来回答个人问题。
- **组织处于生存危机或极早期**：初创公司在 PMF 之前、战时、融资断裂边缘——此时"危机"是真实信号而非病症，"抛弃昨天"也是空转（本来就没有昨天）。先活下来。
- **纯内部职能的价值评估**：法务、合规、财务这类职能的"外部"是社会与监管，反馈周期以年计，四类阈值大多不适用。
- **目标高度争议的组织**：当被要求同时追求三个互不兼容的成果时，四类体检只能诊断不能给解法。

### 作者在书中警告的失败模式

- **把救火当英雄主义**（ce09）—— "管理良好的组织是无趣的组织"。若组织文化在表彰救火，体检结果一定会被抵制。
- **人越多越好**（ce10）—— 判据：高层 >1/10 时间处理摩擦。德鲁克甚至说"四个人的活两天挖完"是错误算法，正确答案可能是"四天甚至永远"。
- **把会多归因为协作多**（ce11）—— 判据：会议 ≥1/4 即结构缺陷。
- **聚焦失败的组织版**（ce12）—— 在办 ≥3 项且都无完成、要事连续无打扰时间 <90 分钟。

### 作者的盲点 / 时代局限

- **"组织越小越接近完美"今天可能不成立**：这与网络效应、平台效应、规模数据优势直接冲突。一个 10 人的公司今天未必比 10 万人的公司更"接近完美"。
- **"会议是结构缺陷的补救"在异步组织里可能相反**：在文档驱动、异步协作为主的组织中，会议可能是弥补异步沟通之不足的必要手段。使用本 skill 时，若用户组织是异步优先，应把"会议 ≥1/4"作为"值得追问"的信号，而非直接定罪。
- **结构性问题的个人化风险**：本 skill 第 3、4 步很可能得出"这超出你的权限"的结论。**请如实说出这一点**，不要为了让用户满意而编造一个个人层面能做的假动作——这正是德鲁克本人被批评最多的一点（诊断说病根在结构，药方却全开给个人）。

### 容易混淆的邻近方法论

- **"精简会议"类效率建议**：它们把会议数量当独立变量优化；德鲁克说会议是结构缺陷的症状，砍会议不治本。
- **OKR / 目标管理**：解决的是"目标是否对齐"，本 skill 解决的是"组织是否在结构上制造了时间浪费"。两者可以并行，但不要互相替代。
